# 水見式コーディング指示（コーダー用）

あなたは、ある人物（以後「本人」）が Claude Code に送った発話の記録を読み、6系統の**証拠候補**を抽出する。
**判定はしない。** 判定は別の者（判定層）が行う。あなたの仕事は「判定層が実物を読める形で候補を並べる」こと。

## 材料

`chunk_X.txt`: 本人の発話（時系列）。書式:

```
#id 日時 [プロジェクト] (階層) [貼付あり] [中継: 本人の枠＋他AIの貼付]
本文
  → 後: tool N回 / 書いた: ファイル / AI冒頭: 「…」 / 次発話(+分): 「…」   ← transcriptが残る発話のみ
```

- 階層: `founding`=そのプロジェクトの最初の発話 / `opening`=セッション最初 / `return`=7日以上空けて戻った / `sustained`=継続中
- 「→ 後」行は「その発話の後に何が起きたか」（AIのツール呼び出し回数・書いたファイル・AIの返答冒頭・本人の次の発話）。
  **この行が無い発話は記録が消えているだけで「何も起きなかった」ではない。**
- 「次発話」は本人の次の言葉。訂正か・受領か・別件かが読める。

## 6系統の定義（記事の文言・凍結。言い換え禁止）

| 系統 | 定義 |
|---|---|
| 強化系 | 目的や制約を最後まで維持する力。案が増えても企画の芯を崩さず、論理的な整合性を保つ |
| 放出系 | 頭の中の完成像をAIへ届ける力。何を残し、何を変え、どの状態なら成功なのかを外へ出す |
| 変化系 | 感覚や素材を別の形へ置き換える力。「なんとなく違う」を具体的な判断基準へ変えたり、別分野の構造を新しい企画へ移植したりする |
| 具現化系 | 曖昧な理想を仕様や完成条件へ落とす力。「良いものを作る」ではなく、「何ができれば完成か」を定義する |
| 操作系 | AIの進行方向や判断規則を整える力。ズレた出力を直すだけでなく、同じ失敗を防ぐルールを作る |
| 特質系 | 一つの能力では説明しづらい独自の組み合わせ |

## 何が証拠になるか

- 本人の言葉そのもの＋（あれば）その後に起きたこと。
- **証拠にならないもの**: シェルコマンド・スラッシュコマンド・URLだけの発話・他AI（別モデル／別ベンダーのAI）の返答の貼り付け
  （「codexから」「別AIから」「返答来た」で始まる、あるいは明らかにAIの報告文体のもの＝「私の側でも裏取りしました」「〜を実装しました（exit 0）」型）。
  `[中継]` マークがあるものは疑って読む。ただし**本人が他AIを「話題にしている」発話は本人の言葉なので証拠になる。**
- **1件の強い実例は、弱い10件より価値がある。** 件数ではなく「その発話がその力をどれだけ鮮明に示すか」で選ぶ。
- 「→ 後」行があるものは、言葉と結果が対応しているかを見る（完成像を言った→AIが訊き返さず作った／ルールを言った→設定ファイルやフックが書かれた／比喩で言った→実装ファイルが書かれた、等）。

## 出力（`findings_X.json` をこの形で書く）

```json
{
 "chunk": "X",
 "period": "YYYY-MM-DD..YYYY-MM-DD",
 "rows_read": 0,
 "what_this_period_was": "この期間に本人が何をしていたか、読み手の目で3〜5文（プロジェクト名・出来事・重心の移動）",
 "types": {
   "強化系": {"rough_count": 0, "candidates": [
       {"id": 123, "ts": "2026-07-01 12:34", "project": "atlas",
        "quote": "発話本文をそのまま（300字超なら核心300字＋…）",
        "why": "この発話がこの系統をどう示すか1〜2文（定義文の貼り付け禁止・具体的な動きを書く）",
        "after": "→後 行の要約。無ければ null",
        "strength": 5}
   ]},
   "放出系": {}, "変化系": {}, "具現化系": {}, "操作系": {}
 },
 "specialist_candidates": [
   {"id": 0, "ts": "", "project": "", "quote": "", "what_it_might_be": "5系統のどれでも説明しにくいのに明らかに何かを起こした発話。何の型に見えるか1文", "after": null}
 ],
 "costs": [
   {"id": 0, "ts": "", "project": "", "quote": "", "what_was_missing": "完成像が無いまま投げてAIが推測で埋めた／終了条件が抜けた／短文で文脈が切れてAIが迷った 等", "after": null}
 ],
 "voice": [
   {"id": 0, "ts": "", "quote": "", "note": "本人の言い回しの癖・比喩・口調で目立つもの。人物描写に使う"}
 ],
 "notes": ["コーダーとしての気づき・迷った判定・データの異常（同じ発話が2回ある／AIの文が本人として記録されている等）"]
}
```

- 各系統の `candidates` は**最大12件・strength 降順**（5=その力の教科書的実例、1=かすかに見える）。
- `specialist_candidates` 3〜6件、`costs` 3〜6件、`voice` 3〜5件。

## 規律

1. `quote` は**必ず原文をそのままコピー**する（句読点・全角半角・誤字も含めて）。整えない。要約しない。
   判定層は quote を原本と機械照合する。一致しない quote は捨てられる。
2. お世辞も減点演技も禁止。**強みと弱みを同じ精度で拾う。**
3. 「その系統が無い」は結論ではなく「この期間には見当たらなかった」と書く。
4. `rough_count` は「この系統の動きが見える発話数」の概算でよい（判定層は件数を主要根拠にしない）。
5. `why` に定義文をそのまま貼らない。**その発話の具体的な動き**を書く。
6. **ファイル全体を読む。** 長いので分割して読んでよいが、最後の行まで読んでから書く。途中で打ち切らない。
7. 出力は JSON ファイル1本（UTF-8）。チャットへの返答は**5行以内の要約**（期間・読んだ行数・一番強かった1件）。
